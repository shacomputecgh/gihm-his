## Acceptance gates (spec §163)

A module is not complete because its interface exists — it must pass functional, security, data-integrity, offline, synchronization and acceptance testing (see `docs/19`).

## Load testing (docs/19 test G, spec §161)

✅ **k6 load suite** (`loadtest/`): clinical mixed workload (register → queue → encounter → lab → pharmacy), read-heavy corridor (dashboard, search, worklists), and sync bursts with idempotent replays — each with functional checks + latency/failure thresholds, scaled per tier with k6 flags (CHPS 5 VUs → national 100 VUs). The suite **caught two genuine concurrency races** on its first real run and both are fixed: patient registration collided on MRN allocation (`Could not allocate a medical record number` / P2002 under parallel creates) and parallel queue check-ins collided on ticket numbers — both now allocate from atomic per-entity sequence counters (`PatientSequence`, `QueueSequence`) baselined in `db:seed`, with regression tests. See `loadtest/README.md` (k6 install, `RATE_LIMIT_MAX` guidance for the API's 300 req/min guard, Postgres note for national-tier write runs).

## Offline field drills (docs/19 Tests B/E/F/H/I)

✅ **Automated offline drills** on top of the sync engine + edge relay:
- **24h-outage backlog** (`tests/edge.test.ts`) — a CHPS facility's full offline day (60 transactions: registrations + linked encounters) drains through a real district tier in application order, in 25-row batches, and lands **exactly once** — verified by entity counts, join integrity (no orphan encounters) and the district's PROCESSED log order matching the facility's.
- **Crash mid-backlog** (`tests/edge.test.ts`, Test H) — the relay dies after the district applied batch 1 but before its cursor persisted; restart re-sends batch 1, the district's transactionId dedupe answers duplicated, and the rest of the backlog still drains — zero loss, zero duplication.
- **Stolen phone** (`tests/devices.test.ts`, Test I) — a device that pushed a batch successfully is revoked (STOLEN, reason recorded); its next batch is refused `403 DEVICE_REVOKED` **before anything is applied** even with a still-valid session token, and the already-pushed data stays intact.
- **Two-device conflict** (`tests/edge.test.ts`, Test D) — two facility devices edit the same lab order offline and sync to the edge; the edge applies the first and preserves the second as CONFLICT with both versions, the losing edit is never relayed (no silent last-writer-wins upstream), and a `keep_client` resolution propagates the corrected result through the relay so the district converges. This drill **caught a real propagation gap**: resolving a conflict updated the entity but never the mutation log row, so the corrected outcome could not relay — `keep_client` now flips the row CONFLICT → PROCESSED (keep_server/manual leave it, correctly, since there is nothing to propagate).
- **National outage** (`tests/edge.test.ts`, Test J) — the facility edge keeps registering patients while the national platform is unreachable (relay fails, cursor untouched); when it returns, the whole backlog drains with the **same entity ids**, exactly once.
- **PWA offline UI drills** (`e2e/offline-drill.spec.ts` — registration, `e2e/offline-dose-drill.spec.ts` — immunization dose; Tests B/C/F) — in a real browser the network is cut (`context.setOffline(true)`): a registration or a vaccine dose queues as exactly one PENDING IndexedDB outbox entry with the exact payload, the app confirms the local save, and on reconnect the `online` event auto-replays it — badge returns to Connected, the entry is consumed, and the record lands in the registry. The drills pre-enrol their sync devices (a fresh context's random device id would be refused `DEVICE_PENDING_APPROVAL` by the docs/21 gate). **Live pending badge ✅** — every outbox change (a write queued offline or drained by a sync) dispatches `gihm:outbox-changed` (`lib/offline.ts`) and the connection provider refreshes the pending count immediately, so the badge shows "Offline 1 pending" the instant work is saved instead of after the 30s poll; the drill asserts it. The outbox now has 7 direct unit tests (`lib/offline.test.ts`, fake-indexeddb): enqueue fires the announcement, syncNow drains processed entries and fires it, failures stay queued for retry (spec §166).

- **Offline reports drill** (`e2e/offline-reports-drill.spec.ts`, docs/26 §6c, Tests B/E) — with the platform unreachable, the Reports page renders the locally cached snapshot (IndexedDB `gihm-report-cache`) clearly marked "Showing the locally cached snapshot from … — the platform is unreachable", never an empty state and never stale figures presented as live; reconnect clears the banner and live data returns.
- **Offline device-lock drill** (`e2e/offline-lock-drill.spec.ts`, docs/26 §6c, spec §97, Tests I/B) — the PIN lock is protection that lives on the device: with the network cut, Lock now still locks, a wrong PIN is refused, the correct PIN unlocks locally (PBKDF2 on-device, zero network), and the session survives — the app keeps navigating offline with no login redirect.
- **Combined offline session drill** (`e2e/offline-combined-drill.spec.ts`, Tests B/C/F) — one disconnected session queues MULTIPLE writes (a vaccine dose + a new-patient registration, prepared online then submitted with the network cut): the badge climbs to "Offline 2 pending", the outbox holds both payloads, and a single reconnect replays them together — the registration is searchable and the dose is in the registry, each exactly once.
- **Mid-submit drop drill** (`e2e/offline-midsubmit-drill.spec.ts`, Tests B/H) — the connection dies WHILE the registration request is in flight (simulated with `route.abort()`): the write is never lost — the failed request falls into the same status-0 path as a clean offline submit, the patient is queued with its exact payload, and a manual "Sync now" (or the next online event) lands it exactly once.
